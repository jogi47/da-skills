# Host: T3 Code

Read with `../SKILL.md`. Where they differ, this file wins. Here a child is a delegated thread, on
whatever provider and model T3 gives it.

## Tools

T3 tools are deferred. Load them with one `ToolSearch` call:
`select:mcp__t3-code__orchestrator_capabilities,mcp__t3-code__delegate_task,mcp__t3-code__task_status,mcp__t3-code__task_cancel,mcp__t3-code__t3_thread_read,mcp__t3-code__t3_thread_send,mcp__t3-code__t3_thread_list,mcp__t3-code__t3_project_list,mcp__t3-code__link_pull_request,mcp__t3-code__watch_pull_request,mcp__t3-code__unwatch_pull_request`

| Need | Tool |
|---|---|
| Find this workspace's project | `t3_project_list`; match the project whose folder is this session's working directory |
| List this workspace's children | `t3_thread_list` with that `projectId`, paged with `cursor` until `nextCursor` is null; never use `allProjects` and never read other projects' threads |
| This coordinator's own id | `currentThreadId` in the `t3_thread_list` result |
| Which children are yours | threads whose `parentThreadId` is your `currentThreadId`. Children with any other parent (an earlier coordinator's included) are the user's own threads |
| Start a child | `delegate_task` with a full brief in `task` (settings below) |
| Follow-up to an idle child | `t3_thread_send` to that child's thread with `mode: "queue"` (or `"auto"`) and only the delta. A send to a finished child starts a new task and returns a new `taskId`: record it in the ledger and use it for `task_status` and `task_cancel`. Never `restart`; `steer` only to correct a turn that is still running. Never to a reviewer, never to the user's own threads |
| Check a child | `task_status`, once, after its completion wakes you. Never on a running child |
| Read a child | `t3_thread_read` with a low `limit` and `maxCharsPerItem`, paged with `afterPosition` |
| Stop a child | `task_cancel`, never `t3_thread_interrupt` on a child |
| A PR you opened | `link_pull_request` with its full URL straight after opening it; `watch_pull_request` while it waits on checks or reviews you are tracking, `unwatch_pull_request` when that wait is over or before you hand the work back. Children never link or watch |

A running child wakes you when it finishes. Name a thread in your reply by its `link`, verbatim.

## Child settings

- No fixed model. Leave `target` out of `delegate_task` and let T3 choose the provider, model and
  options for the child. Do not ask the user about it each time.
- Only when the user names a model, provider or effort for a task: call `orchestrator_capabilities`,
  find it there, and set `target.providerInstanceId`, `target.model` and `target.options` with that
  provider's own option ids. If it is missing or the delegate call fails, say so and stop for the
  user's decision. Never fall back to a native subagent, Workflow or a CLI.
- Set `role` to match the work: `implementation`, `research`, `review`, `design` or `test`.
- Leave `runtimeMode` and `interactionMode` out so the child inherits yours; never pass a higher
  `runtimeMode`. Leave `mode` at its default, `"async"`; never `"wait"`.
- Brief from `../briefs/t3.md`.

## Ledger

`tmp/coordinator/t3-<currentThreadId>.md`. Note `currentThreadId` in the ledger's first line so a
compaction summary carries it. Cleanup touches only other `t3-*` files; `desktop-*` files belong to
coordinators in the Claude desktop app.

## Worktrees

`delegate_task` with `isolation: "worktree"` branches the project this session runs in. When the
session runs in the workspace docs repo, that is the docs repo and not the product repo, so never use it
there for product-repo work. If the session already runs inside the product repo itself,
`isolation: "worktree"` is fine and the steps below are not needed.

This goes against T3's general guidance on purpose: that option branches from the parent's commit in
the wrong repo, so it cannot give a product-repo worktree off the user's chosen base. For a task in a
product repo opened from the docs repo:

1. Check the base first. Fetch each repo the task touches and confirm the base exists on its remote
   (`git -C <repo> ls-remote --heads origin <base>`). Repos can name their dev line differently, so
   check each one.
2. Ask once, before starting anything. Send the batch preview (`../SKILL.md` section 8) with the exact
   `git worktree add` lines, and end it with one question, for example "create these worktrees and
   start the children?". The user's yes covers the worktrees and the children together. Use a worktree
   only when the user asked for one or says yes to one you proposed.
3. Create the worktree by hand, outside the sandbox (`.git/worktrees` is read-only inside it), once per
   repo the task touches:
   `git -C <repo> worktree add --no-track -b <topic-branch> <worktree-path> origin/<base>`
   Branch names are topic names only, with no client names. The base is what the user said, or `dev`
   unless they say otherwise. Put the worktree under the workspace's ignored scratch folder, for example
   `<workspace>/tmp/worktrees/<repo>-<topic>`, so it stays inside the child's writable area; check it is
   ignored (`git check-ignore`) first.
4. Start the child with `isolation: "shared"` and put the worktree path in its brief as the only place
   it may edit. Never let it edit the main checkout.
5. Removing a worktree is a destructive action and needs confirmation.

## What a child loads on its own

Write every brief so it works on any provider. A Codex child, the usual case, loads less than a
Claude one, so the brief fills these gaps:

- **Rules.** Codex reads `AGENTS.md` files on the path from the git root down to its start folder,
  never from folders below it. A child that starts in the workspace root gets the workspace's rules but
  not the product repo's. Name the repo's rules file by absolute path and tell the child to read it
  first: the generated `AGENTS.md` in the repo's main checkout, or `CLAUDE.local.md` where no `AGENTS.md`
  exists. A worktree holds neither file (both are untracked), so always give the main checkout's path.
- **Skills.** A Codex child sees skills under `~/.agents/skills`, `~/.codex/skills` and the workspace's
  `.agents/skills`, not `~/.claude/skills`. Check which folder has a skill before naming it. For one
  only under `~/.claude/skills`, give the absolute path of its `SKILL.md` and tell the child to read and
  follow it.
- **MCP servers.** If the workspace has `.codex/config.toml`, a child started in the workspace root
  gets the servers it lists, under the workspace rules.

## Commit and push

A writing child commits its own work on its own task branch and pushes that branch to its own remote
branch once its checks pass, after confirming `git rev-parse --abbrev-ref @{u}` is not a shared branch.
If it cannot commit or push from its sandbox, it reports that and you do that step. A child that works
on a PR ends with one line: `PR <full URL>, head <SHA>, checks and reviews <state>`.
